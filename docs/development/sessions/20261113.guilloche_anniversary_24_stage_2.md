# De Kosnik 24th anniversary stage 2

Date: 2026-11-13. Status: **approved implementation complete; physical proof pending**.

## Hedcut revision after portrait review

The first stipple/crosshatch portraits were rejected as insufficiently hedcut.
The revised direction is to make the marks describe the form: curved dot rows,
varying dot size, connected feature contours, clear highlights and denser
directional shadows. Remove the repeated diagonal screen from the delivered
portraits. Use the photographs' actual glasses, mouths, hair and coverings;
do not invent features hidden by those coverings.

The C++ implementation now provides `tone-flow/2`, `hedcut/2` and
`hedcut_v2()` through the existing `prepare → resolve → render_svg` API.
Structure-tensor directions guide separated curves; dots follow each curve,
short dashes carry shadows, and source-derived contour sections strengthen
features. The original `/1` recipes remain frozen and tested against their
previous preparation and geometry hashes. All twenty card faces now use `/2`.

The visual reference is [Kevin Sprouls's portfolio](https://www.sprouls.com/),
particularly the long rows, selective lines and open highlights. This revision
uses independent native vector construction, with no raster art in the bills.
The [API contract](../20261113_portrait_rendering_api.md#contour-aligned-hedcut-revision)
records the controls, print assumptions and remaining tone limitations.

## Art direction and complexity

Develop three initial directions, each as a front/back pair:

| Direction | References | Composition | Initial izzi hue candidates |
| --- | --- | --- | --- |
| Dense ceremonial engraving | R02–R05, R07, R18 | Bilateral or fourfold structure, a large crown/medallion system, paired face openings, broad scroll bridges and dense corner fields | `duboisbrown3`, `benitobi`, `wisteria`, `murasaki`, `ivory` |
| Portrait and overlapping rosettes | R06, R08–R11 | Large offset face, a strong numeral counterweight, overlapping discs and a continuous ground; reverse changes the balance | `rokusho`, `asagiiro`, `goldenrod`, `dutchorange`, `goldenyellow` |
| Modern geometric composition | R12–R17 | Stepped fans, interrupted annuli, hexagon/lozenge lattices and sweeping connectors around shaped portrait reserves | Blue study: `rurikon`, `ruriiro`, `asagiiro`, `sohi`, `gold`; green study: `midori`, `aotakeiro`, `hiwamoegi`, `futaai` |

These are candidate hue roles, not measured matches. Select explicitly from
`svg::spectrum<svg::palette_kind::izzi_hue>()`, omitting the `none` sentinel;
record the enum name, resolved RGB and any tint formula. Use a coherent dominant
hue, supporting hue, dark portrait ink and limited accents for each pair.
Compare a reference-led color recipe with its izzi interpretation on identical
geometry. Palette changes must not regenerate portrait marks.

Each face should contain a dominant structure, intermediate motif groups and
fine detail. Vary field extent, orientation, overlaps, interruption, negative
space and hue relationships across the set. Filled bands and shaped fields are
valid tools for the stronger modern compositions. Protect facial highlights
and readable text with authored openings that fit the composition.

The fourfold expansion is measured against the vocabulary **actually used in
stage 1's delivered series**:

1. Inventory the native generator, the Python compositor and visible delivered
   layers. Include script-built scrolls, braids and repeated motifs as well as
   native families. Use the existing guilloche `pattern_family` vocabulary where
   applicable and explicit descriptors for the other mechanisms.
2. Save the baseline family count `B`, its member IDs, source locations and
   example images. Apply the same classification to both stages. Color, seed,
   rotation and a changed repetition count do not create a new family.
3. Require at least **`4 * B` distinct families actually rendered across the
   stage 2 series**. Publish per-face usage too; an available but unused family

4. Give every used family enough visible area to read at final size. Use the

## Portrait and numeral implementation

The [C++ API proposal](../20261113_portrait_rendering_api.md) defines:

```text
prepare(decoded luminance, explicit face mask, tone settings)
    -> owned tone, support, feature-protection and direction fields
resolve(prepared portrait, engraving settings, final size in mm, seed)
    -> inspectable dots and filled hatch/contour geometry
render_svg / render_fragment(geometry, paint, output options)
    -> standalone SVG or composable vector group
```

Author head/face masks against orientation-corrected originals, retaining hair,
ears and visible facial accessories where they contribute to likeness. Remove
full bodies and surrounding scenery. For paired portraits, store an explicit
mask for each selected face or an explicitly authored combined mask. Occluded
faces retain the photographed covering; a failed detector leads to manual
mask authoring, not invented facial detail.

Isolation precedes grayscale tone analysis. Keep source, mask, adjusted tone,
flow field and mark layers inspectable. Use flowing primary hatches, controlled
stippling through lighter facial planes, and a second hatch direction only
where shadow and feature protection allow it. All passes share one coverage
target. The output is vector geometry at the intended physical size, with
versioned recipes, deterministic seeds and bounded memory/work.

Center `24` as one shaped run, including kerning and both actual glyph outlines.
Compute the union ink bounds and area centroid with counters subtracted;
include any painted outline in the measurement. Fit the complete run into the
aperture with uniform scale, then translate its selected visual center to the
aperture center in both axes. Retain both bounds-center and ink-centroid modes;
use ink-centroid weighting for the initial stage 2 comparison, with any authored
optical correction explicit in the recipe. Record the before/after bounds,
centroid and offset. Never average two glyph origins or font advance widths.
This belongs in the lettering/layout helper, independently of the portrait API.
