## 3. Decision summary

Rework the `plans.html` **New** section from a publish-command tutorial
into a two-type proposal intake: a browser form that collects a new
project (`vertical-project` or `short`, plus slug, title, and description)
and opens a prefilled GitHub issue. Approval on GitHub creates the izzi
project directory and starts the planning process with a `plan-v1` draft;
the draft is then published to the portal through the existing
approval-gated publisher and reviewed on the page it was proposed from.

The page no longer shows the publish command, a command builder, a
feedback-round input, a stage select, or a `--dry-run` checkbox. Those
values are fixed: webform plans are always `plan-v1` at the `draft` stage,
and the publish invocation lives only as the repo-side
`scripts/publish-plan-proof.mjs` script.

This plan stages that rework and the two new contracts (the `short` plan
class and the `product_type` field) as gated work packages with defaults,
so each gate can be approved separately.

## 4. The two plan types (formal constraints)

### 4.1 vertical-project (existing)

A vertical-project plan covers a 1080p vertical-format series.

| Constraint | Value |
| --- | --- |
| Format | 1080p vertical video |
| Episodes | `[1–n]` per series |
| Episode length | `[1–3]` minutes each |
| Series size | `[60–100]` episodes |
| Series runtime | `(60–150)` minutes |

The episode-length and series-size ranges interact with the runtime bound:
`60 × 1 min = 60 min` through `100 × 1.5 min = 150 min` satisfy it, while
`60 × 3 min = 180 min` does not. A vertical-project plan must therefore
choose an episode count and duration whose product stays inside the
60–150-minute series envelope, and state the combination explicitly.

This supersedes the older `60–90 episode` figure in
[`20260809.vertical-form.md`](20260809.vertical-form.md).

### 4.2 short (proposed)

A short is a bounded, single-output video, not an episodic series.

| Constraint | Value |
| --- | --- |
| Resolution | `1080p` or `4k` |
| Channel count | `1` or `2` |
| 1-channel orientation | `landscape` or `portrait` |
| 2-channel arrangement | how channels are arranged together in space: `side-by-side vertical`, `horizontal grid`, `vertical grid` |
| Output files | exactly one video file, even for 2-channel work (channels are composited into the single file) |

The arrangement enum is spatial vocabulary, not grid arithmetic. A short
plan states its own channel count, per-channel orientation, cell count, and
canvas layout (for example how many cells per row or column a grid uses);
the three arrangement names classify rather than replace that detail.

## 5. Page rework

The **New** section stops teaching the publish command and becomes a
proposal intake form. The command itself does not disappear from the
system: `scripts/publish-plan-proof.mjs` remains the repo-side publisher.
It is a script, which is exactly the exception the directive allows.

### 5.1 Ladder

Replace the Scaffold / Write to the stage / Publish ladder with the
approval flow the page actually drives:

1. **Propose.** Choose a product type, then fill in vertical slug, title,
   and description. Submit opens a prefilled GitHub issue.
2. **Approve on GitHub.** Approving the issue creates the izzi project
   directory (`docs/development/<slug>/`) and starts planning with a
   `plan-v1` draft.
3. **Review.** The `plan-v1` draft publishes to this page newest-first; a
   `KEEP` advances it, and a `KEEP` on the formal plan unlocks production.

### 5.2 Proposal form

One form replaces the **Build the command** form:

- **Product type** — radio group, values `vertical-project` (default) and
  `short`.
- **Vertical slug** — text input; becomes the izzi project directory slug
  for both types.
- **Title** — text input.
- **Description** — a large textarea where preliminary planning
  information is copied in for GitHub review (for a short, this is where
  resolution, channel count, orientation or arrangement, and the
  single-file note go).
- **Submit proposal on GitHub** — composes the issue and opens it; the
  page never publishes anything itself.

The webform always proposes `plan-v1` at the `draft` stage, so feedback
round, stage, and the `--dry-run` checkbox are removed from the browser
entirely and fixed repo-side. A compact product-type reference panel next
to the form shows both constraint sets from section 4 so a proposer knows
what to put in the description.

### 5.3 Removals

- The **Publish command** `<pre>` template panel — deleted from the page.
- The **Build the command** command-composer and its clipboard copy
  button — replaced by the proposal form.
- The feedback-round, stage, and `--dry-run` controls — deleted.
- The stage-requirements table — folded into the ladder's review step and
  fine print, since stage is no longer a browser input.

## 6. GitHub approval flow

Submitting the form opens a prefilled new-issue URL (the `location.html`
precedent), never a programmatic write:

```text
https://github.com/<owner>/<repo>/issues/new
  ?title=New plan proposal: <title>
  &body=...product type, slug, title, and description verbatim...
```

The issue body carries:

- product type (`vertical-project` or `short`);
- slug, title, and the description text verbatim;
- a fixed line stating the proposal is `plan-v1` at the `draft` stage; and
- a handoff note that approving the issue authorizes creating
  `docs/development/<slug>/` and scaffolding the `plan-v1` draft.

Approval happens on GitHub. The accepted issue payload drives the izzi-side
scaffold (section 8.2), which creates the project directory and the first
draft; the draft is then published to `plans.html` through the existing
approval-gated publisher and reviewed newest-first. Until the user presses
GitHub's final button nothing leaves the browser, and the issue body is
public the moment it is submitted.

## 8. Catalog and script contracts

### 8.1 Catalog

Planning items gain an explicit product type:

| Field | `vertical-project` | `short` |
| --- | --- | --- |
| `product_type` | `vertical-project` | `short` |
| `generation_class` | `plan-vertical` (existing) | `plan-short` (new) |
| `review_scope` | `PLAN-VERTICAL-REVIEW` (existing) | `PLAN-SHORT-REVIEW` (new) |
| `media_kind` | `plan` (unchanged) | `plan` (unchanged) |
| `review_category` | `planning` (unchanged) | `planning` (unchanged) |

`product_type` applies to plan-class items only. Workflow artifacts in the
planning category that are not project plans (for example the
`audio-transcript` artifact) carry no product type and are unaffected.

### 8.2 izzi scaffold

Generalize the existing scaffold so the GitHub approval creates the
directory for either type:

- `scaffold-plan-vertical.mjs` gains `--product-type
  vertical-project|short` (default `vertical-project`), and the short
  starter draft records the short constraints (resolution, channel count,
  orientation or arrangement, single-file output) instead of the
  episode-template skeleton.
- `make plan-scaffold PRODUCT=vertical-project|short NAME=… CONCEPT=…`
  drives both, keeping the existing
  `make plan-vertical-scaffold NAME=… CONCEPT=…` entry working.

### 8.3 Publisher

`publish-plan-proof.mjs` gains `--product-type vertical-project|short`
(default `vertical-project`). The flag selects the `generation_class` and
`review_scope` from the table in 8.1 and stamps `product_type` on the
catalog item. The browser no longer composes this invocation; the script
interface is the only place the command appears.
