This document proposes a small, accessible web review surface for Izzi's
generated artifacts. It extends rather than replaces:

- `docs/development/archive/explore_futures.md`, the authoritative user-supplied source plan;
- `docs/development/sessions/20260808.md`, the initial audit and evolution plan;

- `docs/development/sessions/20260810.md`, the active next-stage implementation plan;

  method.

The immediate target is the existing public GitHub Pages repository
`https://github.com/bdekoz/situationshipin.space`. Its current contents and
design may be replaced. The prototype should publish only a deliberately small
selection from `outputs/review`, allowing collaborators to inspect it from
their own computers and return structured feedback. This is a review transport,
not evidence that a candidate is approved.

`aao-s3` is expressly outside this work. Do not publish credentials, provider
keys, private recordings, unapproved voice material, hidden prompts, raw
conversation traces, or unrelated repository content.

## Current-site and repository audit

The inspected `situationshipin.space` repository is public and small. At the
observed commit `04e2a06ad2f9d71fb88b6ca9ea25a0cecb4d9547`, it contains one
Jekyll page, one approximately 257 KiB image, a minimal layout, and a GitHub
Actions Pages workflow. GitHub Pages is enabled, HTTPS is enforced, and the
custom domain `https://situationshipin.space/` responds successfully.

This is enough infrastructure for a prototype. The current page does not
provide artifact inventories, filters, persistent review state, feedback
export, provenance, or accessibility-oriented review controls. None of its
visual choices need to constrain the replacement.

The Izzi review tree has a very different scale. The observed tree is roughly
2.1 GiB, with the majority of that size in episode-scale MKV output. The file
distribution observed during planning was:

| Size class | Files | Prototype treatment |
| --- | ---: | --- |
| at most 1 MiB | 376 | eligible after explicit selection |
| over 1 MiB through 5 MiB | 154 | exceptional, budgeted selection only |
| over 5 MiB through 25 MiB | 4 | metadata plus a derived ten-frame preview |
| over 25 MiB | 57 | never copy the source; publish a bounded derived preview |

The complete output tree must not be pushed into the Pages repository. GitHub
documents a 1 GiB published-site limit and recommends keeping a Pages source
repository below 1 GiB. Ordinary Git storage warns above 50 MiB per file and
blocks files above 100 MiB. Git LFS cannot be used to serve a GitHub Pages site.
These constraints make thumbnails, filmstrips, compact SVGs, manifests, and
external full-artifact links the appropriate shape.

Large does not mean absent from review. For every selected MKV that exceeds the
portal's object budget, retain a catalog record for the source clip and publish
exactly ten lightweight frames sampled across its complete duration, including
the start and a safe frame nearest the finish. Assemble the same ten frames
into a portrait filmstrip. The source MKV remains outside the Pages repository,
but its path, SHA-256, bytes, duration, dimensions, codec, frame rate, and sample
timestamps remain visible as lineage.

## Desired review experience

The portal should let a collaborator answer four questions without learning
the Izzi build system:

1. What is ready to inspect now?
2. What family, generation class, feedback round, and source produced it?
3. What decision or observation do I want to record?
4. How do I return that feedback without exposing a credential?

The initial interface is a static application built from HTML, CSS, JavaScript,
and a versioned JSON catalog. It should have:

- a concise introduction explaining that `current` is not `accepted`;
- artifact cards with an image, title, family, generation class, feedback
  round, format, dimensions, byte size, source path, and SHA-256;
- filters for visual family, generation class, and review decision;
- decisions `KEEP`, `KEEP-PARTS`, `MORE-LIKE`, `REVISE`, `REJECT`, and
  `DISCUSS`;
- optional observation tags for composition, color, motion, typography,
  legibility, accessibility, provenance, and technical defects;
- a free-form note and optional reviewer label;
- clip-level feedback plus separately addressable feedback for frames 1 through
  10 of every MKV filmstrip;
- browser-local autosave;
- JSON download for selected feedback or the complete local review set;
- an explicitly public, pre-filled GitHub issue route for collaborators who
  want to submit through GitHub;
- a reset control that previews its scope and requires confirmation.

No client-side secret or GitHub token is stored. The issue route opens GitHub's
normal issue form so authentication, identity, preview, and final submission
remain under the collaborator's control. The interface must plainly say that a
GitHub issue is public before opening it. A downloaded JSON file remains the
offline and non-GitHub alternative.

There must be exactly ten unique ordinals and monotonically increasing sample

Technical verification, human review, accessibility review, baseline
promotion, and publication are separate fields. A successful render or public
copy must never mutate another state implicitly.

## Feedback export schema

Feedback belongs to the reviewing human, not to an inferred account state. A
downloaded review package should resemble:

```json
{
  "schema_version": "1.0",
  "portal_build": "<build identifier>",
  "reviewer": "optional human-supplied label",
  "exported_at": "<browser-generated ISO timestamp>",
  "reviews": [
    {
      "artifact_id": "visual-guilloche-round-05-index",
      "artifact_sha256": "<sha256>",
      "decision": "MORE-LIKE",
      "tags": ["composition", "motion"],
      "note": "Keep the registration displacement; vary the white layer.",
      "reviewed_at": "<browser-generated ISO timestamp>",
      "public_submission_acknowledged": false,
      "frame_reviews": [
        {
          "ordinal": 7,
          "time_seconds": 6.667,
          "frame_sha256": "<derived-frame-sha256>",
          "decision": "MORE-LIKE",
          "tags": ["composition"],
          "note": "This is where the rupture becomes useful."
        }
      ]
    }
  ]
}
```

The artifact hash prevents feedback from silently attaching to a later file
with the same name. The portal must retain unknown fields when importing a
newer compatible package, or reject the import with a readable explanation.
Do not infer acceptance from a missing review, a visited card, or elapsed time.
Frame feedback binds to the source-MKV hash, frame ordinal, sample timestamp,
and derived-frame hash. A frame decision does not silently become a clip
decision, and ten accepted frames do not imply acceptance of unsampled motion.

## Aesthetic-corpus review mode

The review portal now has two distinct decision grammars. Generated artifacts
retain `KEEP`, `KEEP-PARTS`, `MORE-LIKE`, `REVISE`, `REJECT`, and `DISCUSS`.
Aesthetic references use `POSITIVE`, `NEGATIVE`, `HOLD`, and `EXCLUDE`.
Mixing these modes into one undifferentiated decision list would make exports
ambiguous, so each catalog item declares its review mode and every exported
decision remains bound to the published derivative and source hash.

The expanded public set is a separate top-level **Style processing** category,
alongside **Proofs for inspection**. It contains all 234 human-selected source
images: 146 from `resources/neon-addict`, 30 from
`resources/tokyo-psychedelic`, and 58 from `resources/noir-vibezz`. The portal
publishes compact JPEG derivatives, not the approximately 232 MiB of source
originals. It shows ten candidates per page, retains filters for each family,
and records each original's path, SHA-256, dimensions, format, byte size,
publication state, and repository state. At the observed Izzi commit these
directories are uncommitted worktree sources; the portal says so instead of
pretending that the base commit contains them. Their generic visual
descriptions remain explicitly pending human review.

### Noir-vibezz source set

The numbered-frame mechanism also simplifies the existing
`resources/noir-vibezz` curation problem. The observed source set contains 58
landscape PNGs in six existing families: `big-combo` (6), `crime-wave` (8),
`la-confidential` (4), `rio` (10), `saigon` (7), and `spidern` (23). Treat each
directory as a source grouping, then divide the combined Noir set into six
stable path-ordered review pages of at most ten images. The source grouping is
retained on every tile and in every export instead of turning the collection
into one long undifferentiated form.

This is a local project aesthetic corpus, not an OpenAI training-conversion
transfer and not authority to send third-party imagery to a provider. The
public review surface contains only the explicitly authorized compact
derivatives. Keep the original image hash and any crop lineage attached to
every label.

### Minimal aesthetic-fit form

Make the frequent decision one click, while preserving honest ambiguity. A
thumbnail click activates its classification controls; the four decisions
remain keyboard-operable and mutually exclusive:

- `POSITIVE`: this image contains visual relationships the project should seek;
- `NEGATIVE`: this image contains visual relationships the project should
  actively avoid;
- `HOLD`: useful or interesting, but not yet classifiable;
- `EXCLUDE`: do not use as aesthetic evidence because of duplication,
  watermark/subtitle, identity, rights, corruption, or another non-aesthetic
  reason.

The public capture surface does not block a quick `POSITIVE` or `NEGATIVE`
decision merely because the reviewer has not supplied a reason. Optional tags
and a note appear when the image is activated. Corpus finalization should ask
for one short reason only when a label would otherwise be too ambiguous to
drive a useful next action:

- composition: threshold, corridor, foreground occlusion, geometric negative
  space, centered silhouette, asymmetry, layered depth;
- light: hard shadow, soft midtone, light shaft, haze, practical lamp,
  reflection;
- palette: black-and-white, amber/burgundy, institutional green, restrained
  selective color, palette drift;
- surface: grain, mesh, rain, glass, tile, fabric, plastic texture;
- subject treatment: silhouette, anonymous figure, intimate close-up,
  recognizable performer, incoherent anatomy;
- production defect: subtitle, watermark, duplicate, compression, crop;
- motion implication: restrained drift, environmental motion, stillness,
  glitch, unwanted camera motion.

The prototype provides tags and a short note. Strength and normalized region
of interest remain later refinements, added only if real review shows they are
worth the extra interaction. A future positive crop means “learn from this
part,” not “discard the rest without evidence.” An exclusion reason stays
separate from a negative aesthetic label: a beautiful frame with a watermark
may be `EXCLUDE`, not `NEGATIVE`.

### Public issue and Codex handoff

Style-processing issues are deliberately scoped to the current ten-thumbnail
page. Preparing an issue performs four visible actions:

1. collect only meaningful reviews on the current page;
2. bind every decision to the derivative and source-image SHA-256 values;
3. compute a stable SHA-256 review identifier over a canonical JSON package,
   excluding only the export timestamp and the identifier field itself;
4. download that exact JSON package and open a public GitHub issue draft that
   names the identifier and includes a suggested Codex handoff prompt.

GitHub still controls authentication, preview, attachments, and final
submission. The reviewer must attach the downloaded JSON before submitting the
issue. The later Codex ingestion step must match the review identifier, portal
build, source commit, derivative hashes, source-image hashes, source-media
hashes, and sampled-frame hashes before acting. It may then update review
records and propose an `izzi-aesthetic-brief-1`; it must treat `HOLD`,
`EXCLUDE`, and unreviewed images as non-positive. A submitted issue does not
authorize a provider request, promote a visual baseline, or imply acceptance
of anything outside its explicit decisions.

### Acceptance into the labeled corpus

An image enters either the positive or negative set only when all of the
following are true:

1. a human explicitly chose `POSITIVE` or `NEGATIVE`;
2. at least one reason tag is present;
3. the source path and SHA-256 still match the inventory;
4. the decision records its review session and timestamp;
5. the reviewer activates one final `Finalize reviewed labels` control for the
   current page or exported package.

The finalization control is intentionally lightweight: it confirms the visible
labels already made and does not repeat consent per image. `HOLD`, `EXCLUDE`,
unvisited, and unlabeled images never leak into either training-aesthetic set.
If two collaborators disagree, retain both reviews and mark the image
`CONFLICT`; do not settle it by majority or last-write-wins without a visible
human resolution.

A record can use this shape:

```json
{
  "image_id": "noir-spidern-0017",
  "source_path": "resources/noir-vibezz/spidern/...png",
  "source_sha256": "<sha256>",
  "family": "spidern",
  "decision": "POSITIVE",
  "strength": 4,
  "reason_tags": ["layered-depth", "amber", "light-shaft"],
  "role": "SUPPORT",
  "region": {"x": 0.18, "y": 0.04, "width": 0.64, "height": 0.88},
  "note": "Keep the receding corridor and foreground occlusion.",
  "review_session": "studio-2026-08-10",
  "reviewed_at": "<ISO timestamp>",
  "finalized": true
}
```

The derived style pack then uses positive records as anchors or supporting
references and converts negative reason tags into explicit constraints. It
does not train directly on a contact sheet, silently infer labels from folder
names, or treat every source frame as positive merely because it was supplied.

### Compile the labels into Seedance generation intent

The labeled corpus should not be handed to Seedance as a directory of 58
unranked images. Compile it into a small, inspectable aesthetic contract that
fits the existing `seedance2ai-v1` authoring workflow:

1. **Select one dominant composition anchor.** Prefer a finalized positive with
   role `ANCHOR`. It governs depth, framing, and negative space for one shot.
2. **Select at most two supporting records.** Use them only for named palette,
   light, texture, or environmental-motion properties. Do not average every
   positive into “reference soup.”
3. **Aggregate positive tags into visible instructions.** Translate labels into
   observable properties such as “bright threshold behind a dark foreground,”
   “restrained black-and-white with one amber register,” and “grain and haze
   retain surface texture.”
4. **Aggregate negative tags into explicit constraints.** State what must not
   appear: generic neon, plastic texture, flat depth, palette replacement,
   subtitles, watermarks, new subjects, face replacement, incoherent anatomy,
   or unmotivated camera motion.
5. **Author one original vertical style frame locally.** Use the selected
   relationships to make a project-owned 1080×1920 composition. Remove source
   text, logos, and recognizable performer identity. Human acceptance of this
   still is the visual gate for provider use.
6. **Send the accepted still, not the corpus.** Resolve the Seedance request as
   image-to-video with the approved style-frame URL. The provider prompt carries
   the compiled contract and asks for narrowly motivated motion.
7. **Review a ten-frame output filmstrip.** Apply clip-level and per-frame
   feedback through the same portal. A rejected frame feeds a concrete negative
   reason into the next canary instead of causing an indiscriminate longer
   prompt.

The compiled record can use this provider-neutral shape:

```json
{
  "schema_version": "izzi-aesthetic-brief-1",
  "brief_id": "duotone-noir-thriller-candidate-01",
  "source_corpus": {
    "inventory_sha256": "<inventory-sha256>",
    "review_export_sha256": "<finalized-review-sha256>"
  },
  "positive_evidence": {
    "anchor_image_id": "noir-spidern-0017",
    "supporting_image_ids": ["noir-crime-wave-0008"],
    "composition": ["bright threshold behind dark foreground", "layered depth"],
    "lighting": ["hard shadow", "restrained haze", "practical light"],
    "palette": ["black-and-white foundation", "limited amber register"],
    "texture": ["grain", "glass reflection"]
  },
  "motion": {
    "camera": ["locked frame or very slow bounded drift"],
    "environment": ["subtle haze, rain, reflection, or fabric movement"],
    "tempo": "restrained"
  },
  "must_preserve": ["foreground/background separation", "intentional black space"],
  "must_avoid": ["generic neon", "plastic texture", "new subjects", "text", "face replacement", "camera warping"],
  "style_frame": {
    "path": "<project-owned-1080x1920-frame>",
    "sha256": "<sha256>",
    "human_aesthetic_approval": "PENDING",
    "provider_transfer": "NOT-AUTHORIZED"
  }
}
```

After the still is accepted and provider transfer and spending are separately
authorized, resolve one short canary through a domain-bound, capability-checked
provider adapter. At the adapter boundary this means:

- `mode`: `image-to-video`;
- start image: the published, approved project-owned style frame;
- aspect ratio: `9:16`;
- delivery profile: requested native 1080×1920, resolved only after the selected
  provider and account expose an exact model, resolution spelling, and quote;
- generation audio: disabled, because the project owns the later audio and
  redubbing workflow;
- prompt: scene action followed by compiled positive grammar, `must_preserve`,
  motion limits, and `must_avoid`;
- duration: one provider-supported shot, later assembled by Izzi into the
  1–3-minute episode form.

Do not infer provider parameters from the aesthetic labels. The adapter still
validates its current provider contract, account tier, price, duration, and
resolution before submission. The aesthetic compiler produces creative intent;
the provider adapter produces an authenticated request.

A successful provider response proves only that the request ran. Promote its
look only after the ten sampled frames and full clip receive human review. The
positive/negative corpus then becomes a compact feedback memory: it tells the
next prompt which relationships to preserve and which observed failures to
avoid without repeatedly uploading or re-explaining the entire reference set.

### Three-stage aesthetic generation contract

Use the same form-first discipline as the other Izzi workflows, with a distinct
formal execution stage between evidence curation and artistic refinement.

#### Stage 0: label and freeze the evidence

- inventory all 234 portal source images by stable path and SHA-256, while
  compiling only the explicitly selected project collection into a brief (the
  initial Duotone Noir brief starts with the 58 Noir Vibezz images);
- review them in path-stable pages of at most ten;
- finalize explicit `POSITIVE`, `NEGATIVE`, `HOLD`, and `EXCLUDE` decisions;
- resolve conflicts rather than overwriting one collaborator with another;
- compile the accepted labels into `izzi-aesthetic-brief-1`;
- author and hash one original 1080×1920 style frame;
- retain provider transfer and human approval as pending fields.

Stage 0 is complete when the evidence, labels, reasons, brief, and original
style frame are reproducible and inspectable. It does not contact Seedance.

#### Stage 1: prove constraint-bound generation

Run one provider canary from the frozen style frame and aesthetic brief. This
stage is governed by formal contracts rather than a free-form prompt pasted by
hand:

- validate the aesthetic brief and resolved request with versioned JSON Schema;
- require exact source, review-export, style-frame, and prompt hashes;
- reject unknown decision values, missing positive/negative reasons, stale
  source hashes, missing authority states, non-portrait style frames, and
  unsupported provider parameters;
- resolve positive grammar, `must_preserve`, motion, and `must_avoid` into a
  deterministic prompt document before submission;
- keep credentials as a local reference, never a schema value;
- record the exact provider domain, model route, 1080p spelling, aspect ratio,
  duration, audio setting, price estimate, and approval state during preflight;
- first emit a redacted dry-run request; contact the provider only after the
  existing transfer and spending gate permits it;
- probe the returned clip, retain its provider receipt privately, and generate
  a public-safe ten-frame review package.

Test positive and negative schema fixtures. A Stage 1 pass means the complete
mechanism worked with formally bounded inputs and produced a reviewable clip.
It does not mean the aesthetic is accepted.

#### Stage 2: refine with human review

Review the Stage 1 clip as a complete temporal object and review frames 1
through 10 independently. Humans may keep the clip, keep named parts, request
more like a frame, revise, reject, or discuss. Convert specific feedback into
one of four visible changes:

1. promote or demote positive supporting evidence;
2. add or narrow a negative constraint;
3. revise the original style frame;
4. change one declared motion or composition variable.

Freeze each revised brief and style frame as a new candidate; do not mutate the
Stage 1 evidence. Generate A/B canaries by changing one named variable when
possible. Repeat Stage 2 until humans accept a visual direction or document a
stop. Silence, technical success, issue closure, and ten individually positive
sample frames do not imply full-clip acceptance.

## Provider identity correction: Seedance2AI

### Two similar domains are different providers

The existing Izzi credential guide, private configuration, API scripts, and
completed canaries are bound to `seedance2ai.io`. The newly supplied URL,
`https://seedance2ai.ai/pricing`, belongs to a different independently operated
service. Its terms explicitly say that `seedance2ai.ai` is not affiliated with
or endorsed by ByteDance. An account, subscription, credit balance, API key,
or support history at one domain is not evidence of any state at the other.

Do not solve this distinction by changing a hostname in the existing client.
The local `.io` key must never be sent to `.ai`. Preserve the historical
`seedance2ai-io-v1` adapter and evidence as observed history. A future `.ai`
route needs its own account observation, credential, terms receipt, capability
preflight, and adapter identifier. The `.ai` public site exposes a browser
studio, but the review found no public video API reference or API-key contract;
automation remains `UNAVAILABLE` until such evidence exists.

### Model and resolution finding

The model-selection hypothesis does not explain the prior `.io` discrepancy.
Two `.io` requests used `quality_tier: standard` plus `resolution: 1080p`, and
one diagnostic used `quality_tier: pro` plus `resolution: 1080p`; all three
provider originals measured 720×1280. The Pro diagnostic therefore already
tested the proposed configuration correction.

The `.ai` service presents a different catalog:

| `.ai` model | Exposed resolutions | Observed credit rate without video input | Best role here |
| --- | --- | ---: | --- |
| Seedance 2.0 | 480p, 720p, 1080p, 4K | 6, 12, 30, 70 credits/output second | only current `.ai` Seedance route that claims native 1080p |
| Seedance 2.5 | 480p, 720p | 10, 20 credits/output second | up to 30-second, reference-rich 720p continuity canary |
| Seedance 1.5 Pro | 480p, 720p, 1080p | 2, 5, 10 credits/output second | older, non-video-reference fallback; not “Seedance 2.0 Pro” |

There is no `Seedance 2.0 Pro` entry in the observed `.ai` catalog. Seedance
2.5 currently cannot satisfy the preferred 1080×1920 delivery requirement
because its own page exposes only 480p and 720p. For a future `.ai` resolution
canary, choose **Seedance 2.0 at 1080p**, not Seedance 2.5. A ten-second request
without video input is listed at 300 credits. When a video reference is used,
the 1080p rate becomes 20 credits per second of input plus output; images and
audio do not add billable duration.

This remains a plan, not submission authority. Before spending anything:

1. the human operator confirms which domain holds the paid account;
2. record the authenticated plan name, credit balance, model menu, and exact
   pre-submit quote without changing the account;
3. use a new domain-bound credential record if the account is `.ai`;
4. run one five-second, portrait, Seedance 2.0, 1080p canary from a
   project-owned accepted style frame after separate transfer and spend
   authorization;
5. download the provider original immediately and require `ffprobe` to report
   exactly 1080×1920 before any second request;
6. retain the ten-frame review gate and stop on any model, price, or resolution
   mismatch.

## Provider investigation: Z-Image Turbo / Image Creator AI

### Recommendation

Keep `zimageturbo.ai` as a **canary-only alternate aggregator**, not the next
production adapter. The official Alibaba Tongyi-MAI Z-Image Turbo project is a
text-to-image model; it is not a video generator. The similarly named
`zimageturbo.ai` site says it is an independent service and offers many
third-party image and video models under the Image Creator AI product.

The aggregator does expose a useful-looking video form: text-to-video,

## Provider investigation: OpenAI Sora

### Recommendation

Do not replace Seedance with Sora for the production episode pipeline. This is
not a quality judgment. OpenAI's current official notice says that the Sora web
and app experiences ended on April 26, 2026 and that the Sora API will be
discontinued on September 24, 2026. On the August 10 investigation date, that
leaves only 45 days of API life. A new provider-specific implementation would
be throwaway work before the proposed 10-, 30-, and 60-episode ramps begin.

Sora remains reasonable for one explicitly temporary comparison canary if the
team values the evidence enough to pay for it. Such a canary must not become a
new production dependency, and all returned assets must be downloaded,
probed, hashed, and stored locally before their provider expiry.

### Current official capability fit

The remaining Sora API is unusually well aligned with several Izzi experiments:

- `sora-2` creates 720×1280 portrait video with synchronized generated audio at
  $0.10 per generated second;
- `sora-2-pro` lists portrait outputs at 720×1280 for $0.30 per second,
  1024×1792 for $0.50 per second, and 1080×1920 for $0.70 per second;
- text and image are inputs, while video and synchronized audio are outputs;
- an `input_reference` image controls the first frame and must exactly match the
  target resolution; JPEG, PNG, and WebP are accepted;
- non-human reusable characters fit the four-animal Here Lies Trouble concept;
  character source clips work best at two through four seconds, one generated
  video may contain up to two characters, and human-likeness uploads are
  blocked by default without separate eligibility;
- the API exposes asynchronous job state, MP4 download, a thumbnail, and a
  spritesheet, which map cleanly to the existing Izzi poll, receipt, and review
  package;
- Batch supports shot-list generation, stable custom IDs, and image references,
  but completed batch video downloads remain available for only 24 hours;
- extensions may add up to 20 seconds at a time and continue one result to a
  maximum of 120 seconds, but extensions do not accept character or image
  references.

Sora does not accept recorded audio as a video-generation input. The existing
transcription, scene-cut, voice-consent, redubbing, and final FFmpeg mux stages
would remain necessary. Generated synchronized audio should be disabled or
discarded for the projects that retain their recorded and transformed voices.

The official guide and API reference are inconsistent as observed. The guide
says a generation may be as long as 20 seconds and identifies 1080×1920 as a
Pro output. The create-video API reference lists only 4-, 8-, and 12-second
durations and lists 720×1280, 1280×720, 1024×1792, and 1792×1024 sizes. A canary
must therefore perform a live, no-spend capability preflight and treat the
request schema actually accepted by the endpoint as evidence; documentation
alone is not enough to promise 1080p or 20 seconds.

### Cost implications for the accepted vertical form

At the listed 1080×1920 Pro price, one 10-second canary costs $7 before retries.
A complete 1–3-minute episode contains $42–$126 of generated output. Sixty such
episodes contain $2,520–$7,560 of generated output, and ninety contain
$3,780–$11,340, before alternate takes, failures, extensions, editing, audio
work, or local assembly. This is inappropriate for form discovery. If a Sora
comparison is approved, use one 8-second 720p standard shot ($0.80) or one
8-second 1080p Pro shot ($5.60), not an episode-scale run.

### Minimal non-production canary

If explicitly authorized before the shutdown date:

1. add a provider-neutral OpenAI credential reference; never reuse
   `SEEDANCE_KEY` or place an OpenAI key in JSON;
2. freeze one project-owned 9:16 style frame and one
   `izzi-aesthetic-brief-1` record;
3. preflight model availability, accepted duration, accepted size, current
   price, account rate limit, and the shutdown warning without submitting;
4. resolve one 8-second request with `sora-2` at 720×1280 or `sora-2-pro` at
   1080×1920 only if the live endpoint confirms it;
5. record the prompt, style-frame hash, model snapshot, dimensions, duration,
   and maximum approved spend;
6. submit once, poll asynchronously, and download the MP4, thumbnail, and
   spritesheet immediately;
7. probe and hash the result, mux project audio only in the local Izzi stage,
   and publish only the normal ten-frame review derivative;
8. compare the same frozen brief against Seedance using composition fidelity,
   palette fidelity, motion restraint, temporal defects, resolution, latency,
   and cost;
9. archive the evidence and remove Sora from active provider choices before the
   API shutdown unless OpenAI publishes a separately documented successor.

The enduring implementation should be a provider-neutral adapter with
capability discovery, dry-run resolution, cost ceilings, async submission,
download, probing, and receipts. Seedance and the temporary Sora adapter should
map into that contract rather than leaking provider spellings into the scene or
aesthetic schema.

## Accessibility and visual-review requirements

The portal itself should embody Izzi's accessibility goals while avoiding a
premature conformance claim. Implement and test:

- semantic landmarks, headings, lists, forms, labels, and status messages;
- a skip link and logical focus order;
- complete keyboard operation and visible focus;
- status text and symbols so color is never the only signal;
- high-contrast controls and readable type at browser zoom;
- responsive cards that work on phones and desktops;
- intrinsic image dimensions to reduce layout movement;
- useful alternative text describing what the proof contains and what it does
  not prove;
- numbered frame controls whose accessible names include clip title, ordinal,
  timestamp, and current decision;
- reduced-motion behavior and no autoplay;
- no flashing portal chrome;
- error messages connected to the control that needs correction;
- a compact text/table view for people who do not want a visual grid.

Generated art may deliberately be wild, dense, low-contrast, or difficult to
read. The portal must distinguish that subject matter from the accessibility of
the surrounding review controls. A candidate is not called WCAG 2.2 conformant
until the applicable automated and human checks are actually complete.

## Publication and storage tiers

Use three explicit tiers:

### Tier 1: GitHub Pages review media

Small thumbnails, ten-frame filmstrips, compact PNG/SVG proofs, JSON manifests,
and HTML tables. A Tier 1 catalog item may describe a Tier 3-sized source MKV
when the source itself is not copied and every public derivative passes the
Tier 1 budget. Enforce per-file and total-build budgets in the staging script.
This is the only tier implemented by the first prototype.

### Tier 2: bounded downloadable artifacts

Selected larger files may later be attached to a versioned GitHub Release when
that is appropriate for occasional download. Release assets are not a general
video-streaming design. Each use requires publication, provenance, privacy,
and retention review.

### Tier 3: episode-scale media service

Full MKV episodes and large generative sets require a separately selected
media host or delivery system with known cost, bandwidth, retention, and access
controls. Make this a later decision informed by actual collaborator usage.
Do not silently substitute Git LFS, repository blobs, or `aao-s3`.

The Pages portal can carry stable metadata and a link for a Tier 2 or Tier 3
object, but the link must declare whether it is public, its expected size, and
whether the reviewer is seeing the full temporal artifact or only a preview.

## Staging and deployment workflow

Implement the prototype as a reproducible export rather than hand-copying a
directory:

1. select an allowlist of artifact and MKV source paths;
2. reject missing files, paths outside the Izzi repository, disallowed media
   types, and direct-publication objects over the configured limit;
3. measure dimensions, bytes, and SHA-256 values;
4. for each selected MKV, use its measured duration to sample exactly ten
   frames at evenly spaced positions from start to safe finish;
5. create ten numbered lightweight thumbnails and one portrait filmstrip while
   retaining timestamps and hashes for every derivative;
6. copy eligible direct artifacts and derived previews into a dated portal
   directory without changing source artifacts;
7. generate the catalog and build manifest;
8. validate JSON, HTML structure, asset links, duplicate IDs, hashes, sample
   order, frame ordinals, source-media lineage, and size
   budgets;
9. exercise keyboard, local-save, clip and per-frame feedback, export, reset,
   filter, and public-issue flows
   in a local browser;
10. inspect desktop and narrow-viewport screenshots;
11. commit the bounded portal change to `situationshipin.space`;
12. deploy with its existing GitHub Pages workflow and verify the live URL and
    Actions result.

The first prototype may use a hand-maintained allowlist. Before the second
publication, encode it as a checked configuration and a small staging command
so later review packages cannot accidentally sweep in the whole output tree.

The portal repository should retain only the currently published small review
set plus intentionally preserved historical review releases. Replacing the
current set must be explicit; avoid accumulating every generation pass in Git
history without a retention policy.

## Review lifecycle

Use the following state flow for each artifact:

```text
STAGED -> PUBLISHED -> REVIEWED -> RESOLVED -> optionally PROMOTED
```

`REVIEWED` means a visible human decision was received. `RESOLVED` means Izzi
has imported or otherwise dispositioned that decision. `PROMOTED` requires a
separate baseline decision. A negative decision remains valuable review
evidence and need not be deleted.

For the first prototype, feedback returns as downloaded JSON or a public GitHub
issue. A later importer can validate artifact IDs and hashes, append a receipt
to the Izzi trace, and update the relevant feedback round. The importer must
not treat issue closure as aesthetic acceptance unless the issue explicitly
records that decision.

## Security, privacy, and consent boundary

- Publish only artifacts already authorized for redistribution and selected by
  path for this portal build.
- Treat GitHub Pages, repository history, Actions logs, and GitHub issues as
  public surfaces.
- Never place `SEEDANCE_KEY`, environment dumps, cookies, tokens, voice-consent
  records, raw private audio, or private collaborator details in the site.
- Do not add analytics, third-party trackers, remote fonts, or embedded
  comment services to the prototype.
- Store draft feedback in the collaborator's browser only until they explicitly
  download it or open the public issue workflow.
- Explain that clearing browser storage can remove an unexported draft.
- Keep training-conversion transfer state separate and `NOT-SHARED`.
- Do not record or reconstruct hidden chain-of-thought.

## Prototype acceptance conditions

The first public prototype is complete when:

- six selected static Izzi proofs and four selected MKV filmstrips render at
  the custom Pages URL;
- the separate Style processing category exposes exactly 234 compact
  derivatives—58 Noir Vibezz, 30 Tokyo Psychedelic, and 146 Neon Addict—ten
  per page without publishing source originals;
- each MKV record has exactly ten numbered frames distributed from start to
  safe finish, and every frame accepts an independent decision, tags, and note;
- the total staged artifact payload and each object pass declared budgets;
- every item displays provenance and a content hash;
- filtering and all review decisions work with mouse and keyboard;
- refresh preserves local draft feedback;
- JSON export contains the artifact hashes and round-trip validation succeeds;
- the GitHub issue action warns that submission is public, scopes style reviews
  to the current page, downloads the exact SHA-256-identified JSON package,
  includes the suggested Codex handoff, and contains no credential;
- narrow and desktop layouts have been visually inspected;
- missing-image and disabled-storage conditions fail readably;
- the Pages workflow succeeds and the live deployment is checked;
- the Izzi trace records source hashes, portal commit, checks, and deployment
  receipt;
- no source MKV, source audio, secrets, private audio, provider key, or
  `aao-s3` operation is present.

Human judgments on the displayed art remain pending after these technical
conditions pass.

## Evolution after the prototype

### Phase 1: bounded public canary

The ten-proof portal is deployed and received positive first-pass feedback.
The second publication now adds the 234-item Style Processing category and its
hash-bound public-issue handoff at portal commit
`58e426c7271da76a906d3c81e5c9425f4ed5f553`. Collect real reviews from the
project owner and one collaborator before adding another corpus or control.

### Phase 2: reproducible Izzi export

The image and MKV derivative generators, hash inventory, size checks, and
deterministic ten-frame preview are implemented for this bounded publication.
Next, replace the current hand-maintained selection with one reviewed Izzi-side
allowlist/configuration while retaining the temporary-package validation gate.

### Phase 3: review ingestion

Add a local command that imports downloaded feedback JSON or a deliberately
selected GitHub issue. Validate schema, portal build, artifact ID, and hash;
then write an append-only receipt and update the corresponding review round.

### Phase 4: collaborator workflow

After real usage, decide whether public GitHub issues are sufficient, whether
private feedback is needed, and whether a small authenticated service is worth
its operational and privacy cost. Do not build a server before the static
workflow demonstrates the need.

### Phase 5: large-media references

Measure demand for full-motion review, choose a storage and delivery tier, and
prototype explicit links from filmstrips to full episodes. Cost, privacy,
bandwidth, expiry, and provenance must be visible before transfer.

Keep frame-level review when full media becomes available: it is useful shot
and composition evidence even after a reviewer can play the clip. Add optional
time-range notes later rather than replacing the ten stable sample anchors.
