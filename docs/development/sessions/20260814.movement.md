# Response 1 — generation_movement plan (reassessment + developed plan)

## Reassessment

The brief asks for a third generational surface alongside
`generation_pattern` (`docs/generative_patterns/`) and `generation_color`
(`docs/generative_colors/`): **generation_movement**. The two variants are
complementary and share one serialization contract:

- **one-path** — an animation follows a generated SVG path element from
  start to finish, where the path itself is produced by any
  `generation_pattern` family (roulette trochoids, surface-tension
  contours, guilloche curves, moire orbits, hamonshu waves);
- **multi-path** — camera tracking plus multiple layered paths, including
  ripple/raindrop/wave movements along a path, and camera-movement
  descriptions extracted from real clips (here-lies-trouble master,
  `resources/time-to-die-ai/seed-video-corpus/Blade.Runner.Final-Cut.4k-cut-5-1080p.1.mkv`).

The existing izzi text-overlay already models per-run timing (start,
duration, delay) for danmaku; movement reuses that timing model for path
travel. Determinism is inherited from the pattern families (paths are pure
functions; seeded RNG where stochastic).

## Smallest serialization API / interface

One compact JSON **movement document** per animation; the smallest contract
is a path *reference* plus timing — no pixel arrays, no frame lists:

```json
{
  "schema": "izzi.movement/1",
  "viewport": [1920, 1080],
  "duration": 194.733,
  "camera": {
    "path": { "family": "roulette", "kind": "trochoid",
              "params": { "r": 120, "k": 0.8 }, "samples": 240 },
    "start": [0, 540], "end": [1920, 540],
    "duration": 194.733, "easing": "linear"
  },
  "layers": [
    { "id": "ripple", "path": { "family": "surface-tension", "kind": "paired-drops" },
      "duration": 12.0, "easing": "ease-in-out" }
  ]
}
```

C++ surface (`src/izzi-svg-movement.h`, new):

- `enum class easing { linear, ease_in, ease_out, ease_in_out }`
- `struct movement_path { string family, kind; json params; size_t samples; bool reverse; }`
- `struct movement_segment { movement_path path; point start, end; double duration; easing ease; }`
- `struct camera_spec { movement_path path; point start, end; double duration; easing ease; }`
- `struct movement_document { area viewport; double duration; camera_spec camera; vector<movement_segment> layers; }`
- `point_2t sample_path(const movement_path&, double t)` — point + tangent at time t (pure, deterministic)
- `string emit_movement_json(const movement_document&)` / `movement_document movement_from_json(string_view)`

## Developed plan

1. **Docs** — `docs/generative_movement.md` + `docs/generative_movement/`
   (`index.md`, `movement.md` family entry, `assessment_plan.md`),
   mirroring `generative_colors`; family name **movement**.
2. **API** — implement `izzi-svg-movement.h` (types above) with
   `sample_path` wired to the pattern families' pure math (roulette,
   harmonograph, surface-tension) and seeded path variants.
3. **One-path** — `follow_path(doc, element)` moves an element/camera along
   the sampled path start→end over `duration` with easing.
4. **Multi-path** — `movement_layer`s composited over a camera track
   (pan/zoom deltas); ripple/raindrop/wave expressed as surface-tension and
   hamonshu paths.
5. **Video extraction** — `scripts/extract-movement.py --input <clip>
   --output movement.json`: ffprobe duration/geometry; ffmpeg motion pass →
   per-interval camera deltas `{t, dx, dy, scale}` → camera_spec. Exercise on
   the here-lies-trouble master and Blade Runner cut-5.
6. **Examples/tests** — `examples/movement-one-path.cc`,
   `movement-multi-path.cc`, `movement-ripple-raindrop-wave.cc`; CTest

   Make targets; generation-baseline coverage.

## Built pipeline (implemented 2026-08-14)

`scripts/build-subtitles.py`:

1. **Event timing** — ffprobe the subtitle stream's packets
   (`pts_time` / `duration_time`); display-end packets do not start events.
2. **OCR text** — for each event, burn the subtitle onto its mid frame with
   ffmpeg (`[0:v][0:s:<ordinal>]overlay`), crop the bottom band
   (y 0.83–0.96 h), upscale ×2, and OCR with tesseract (`--psm 6`);
   noise-filtered lines must contain a real word (≥3 letters).
3. **SRT** — write cue timing + text.
4. **Burn** — ffmpeg libass with
   `force_style=FontName=Atkinson Hyperlegible`; `-ss`/`-t` follow `-i` so
   libass keeps the original cue timeline.

# Response 3 — synthesized large-file-local proofing plan

## Problem

situationshipin.space enforces 16 MiB per artifact and a bounded total
payload; full-resolution local outputs (MKV masters, 4K stills, WAV masters)
do not fit. Full-resolution proofing is still useful for humans reviewing
video accuracy.

## Find, link, review

1. **Find** — local proof root `outputs/review/full-resolution/<artifact-id>/`
   with `proof.json` per artifact (path, sha256, size, ffprobe metadata) and
   an aggregate `outputs/review/full-resolution/index.json` + markdown index.
   `scripts/proof-local-outputs.py` walks build/review trees, hashes, probes
   (ffprobe), and refreshes the index (`--dry-run` default).
2. **Link** — portal review pages for large artifacts carry a
   `local_proof` metadata block (path, sha256, size) and a "local
   full-resolution proof" note linking the local index. The site hosts only
   the bounded proxy; `local_proof` is metadata-only (the checker verifies it
   is never a published path).
3. **Review** — reviewer uses the web proxy for gestalt; opens the linked
   local full-resolution file for frame-accurate checks; the review JSON
   records both proxy sha256 and local proof sha256.
4. **Coverage** — here-lies-trouble masters, time-to-die attempted-render
   MKVs, asama loops, blade-runner cuts (read-only resources), voice WAVs.

# Response 4 — synthesized asama-loops plan (API example)

## Clip facts (probed 2026-08-14)

`resources/asama-loops/asama-01-roji-1.0-5px.mkv` — 1920×1080, h264 + aac,
30 fps, 194.733 s, 24.9 MB. An alley (roji) loop; the movement of interest is
the camera tracking through the narrow lane.

## Example: re-create the movement with the proposed API

```cpp
#include "izzi-svg-movement.h"

int
main()
{
  using namespace svg;

  movement_document doc;
  doc.viewport = { 1920, 1080 };
  doc.duration = 194.733;   // source clip duration in seconds

  // One-path camera: track through the roji along a roulette path.
  doc.camera = camera_spec{
    movement_path{ "roulette", "trochoid",
                   { { "r", 120 }, { "k", 0.8 } }, 240 },
    { 0, 540 }, { 1920, 540 }, doc.duration, easing::linear
  };

  // Multi-path layers: ripple, raindrop, wave along pattern paths.
  doc.layers = {
    { "ripple",   movement_path{ "surface-tension", "paired-drops", {}, 60 },
      12.0, easing::ease_in_out },
    { "raindrop", movement_path{ "surface-tension", "vertical-chain", {}, 60 },
      9.0, easing::ease_in },
    { "wave",     movement_path{ "hamonshu", "nested-current-scrolls", {}, 90 },
      16.0, easing::linear },
  };

  emit_movement_json(doc, "asama-01-roji.movement.json");
  return 0;
}
```

Verification: `sample_path(camera.path, 0)` == start and
`sample_path(camera.path, duration)` == end; extracted camera deltas from the
clip (Response 1 step 5) should approximate the same pan when the same
start/end are chosen. The same spec format is the interface for
here-lies-trouble and Blade Runner cut-5 camera descriptions.
