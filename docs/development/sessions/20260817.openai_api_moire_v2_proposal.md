## 3. Scope interpretation

**Tune** means tighten the existing three field kinds against the reference
grid character: line spacing and angle ranges, concentric radius/aspect
stepping, radial angular spans, wave amplitude/frequency, and the
degeneration amounts — plus the beat-period statistics and render-profile
coverage the family docs already list as open items.

**Extend** means additive `field_kind` values inspired by the nine archive
families, staying inside the independently-authored discipline:

- dot/point grid (`mi-dg`), negative-positive inversion (`mi-np`),
  square grid (`mi-sqg`), slanted line grid (`mi-slg`), rotated line grid
  (`mi-rlg`), and variable grid (`mi-vg`);
- the closest existing matches (line grids ≈ `mi-clg`, radial grids ≈
  `mi-rg`) stay tune-only;
- hybrid (`mi-hyb`) becomes a new two-family composition helper rather than
  a copied archive plate.

No archive path data is extracted or embedded. The `archive-geometry-used`
metadata remains `false`; the archive informs spacing, density, angle
relationships, and visual character only.

## 4. How the sol-5.6 API round would run

Same loop as the guilloche v2 round, per the official OpenAI documentation:

- Model `gpt-5.6-sol` via the Responses API, Flex processing (`service_tier:
  "flex"`, Batch rates), reasoning effort high on design turns and medium on
  mechanical edits.
- Tools: `apply_patch` for code changes and structured outputs for a

  `image_generation` stay disabled (code changes only, no testing, no image
  production).
- Deliverable per turn: unified diffs plus a JSON manifest; a human or Codex
  applies and compiles locally.

## 6. Reference policy (no text, no numbers)

Each work package's prompt states the policy explicitly: the archive plates
are geometry references only. Sol-5.6 may use grid spacing, density, angle
relationships, inversion structure, and texture character; it must ignore
any text or numerals and must never extract or reproduce archive path data.
The archive is a user-licensed publication set, so the existing
independently-authored provenance and `archive-geometry-used=false`
metadata are preserved rather than weakened.

## 7. Compression / packaging recommendation

The billed unit is tokens, not bytes, so byte compression does not reduce
cost. The real optimizations are sampling, rasterizing, and caching.

**Sources — plain text, no compression.** The header and example are about
35 KB (~10K tokens). Send them with `===== FILE:` separators, full fidelity.

**References — sample, rasterize, then base64.** The archive is SVG, and
`gpt-5.6-sol` vision input accepts raster formats, not SVG:

- Rasterize a bounded sample with Inkscape: about five plates per family
  (~45 plates) at 1024 px wide, PNG, which is ~960 image tokens per plate at
  the 32px-patch rule and roughly 43K tokens for the set (about $0.11 per
  read at the Flex input rate).
- Sending all 549 plates is not justified: ~527K tokens (about $1.32 per
  read) with little marginal guidance. Full-resolution zoom is allowed only
  for up to 3 plates per zoom turn and at most 6 zoom turns total.
- Transport: base64 data URLs for the sampled set; the Files API with
  `file_search` only if the same set must persist across many turns.

## 8. Cost estimate against the $50 balance

Official rates for `gpt-5.6-sol` (Flex/Batch processing, per 1M tokens):
input $2.50, cached input $0.25, cache writes $3.125, output $15.00.
Reasoning tokens are billed as output tokens.

| Scenario | Math | Total |
|---|---|---|
| 1. One-shot survey | input ~55K (cache write $0.17) + output ~15K ($0.23) | ~$0.40 |
| 2. Full round M1-M5, 30 turns, cached sample | first turn ~$0.40; turns 2-30: cached read ($0.014) + deltas ~4K ($0.013) + output ~12K ($0.18) = ~$0.21 each = $6.1; 6 zoom turns ~$0.5 each = $3.0 | ~$9.50 |
| 3. Full round with Batch/Flex for mechanical bulk | about half of the per-turn fees at half rate | ~$5-6 |
| 4. Worst case: all 549 plates uncached every turn | 30 x (input ~$1.32 + output ~$0.30) | ~$49 — **budget edge** |
| 5. Tight run: sampled, cached, Batch for bulk, 25 turns | smaller outputs | ~$4-5 |

Verdict: the recommended path (scenario 2 or 3) fits inside $50 with wide
margin. The budget is only at risk if the full archive is rasterized and
sent uncached every turn, which the guardrails below prohibit.

Guardrails (mandatory before spend):

1. Ship the ~45-plate 1024 px sample as the default; full archive rasterization
   is never sent in a turn.
2. Keep the source + reference prefix byte-stable across turns so prompt
   caching applies; carry `previous_response_id`.
3. Reasoning effort high only on M1/M2/M3 design turns; medium elsewhere;
   never pro mode.
4. Set `max_output_tokens` per turn (e.g., 20K) to bound reasoning spend.
5. Use Batch/Flex for M4/M5 mechanical edits if turnaround allows.
6. Check `usage.output_tokens_details.reasoning_tokens` after every
   package; stop the round at $40 cumulative.
