# Izzi portal — plans.html "New" plan-creation section (proposal)

Date: 2026-08-16

Status: `PROPOSAL; ZERO-SPEND; AWAITING-APPROVAL`

## Why now

`https://situationshipin.space/plans.html` tells a reviewer how to review
plans, but the page itself never says how a new plan gets added. The
publish workflow lives only in the situationshipin.space README. This
proposal adds a static **New** section above **Review** on `plans.html` so
the plan-creation path is discoverable in the same place plans are reviewed.

## What the section is

- **Position:** between the **Status** summary section and the **Review**
  section of `plans.html` (newest DOM sibling before
  `<section class="review-section">`).
- **Heading:** `New`, with `id="new-title"` and
  `aria-labelledby="new-title"` on the section.
- **Scope:** static guidance plus a copyable publish command. The site stays
  static: nothing is submitted from the browser, and publication remains
  repo-side and approval-gated. This section *explains and prepares* the
  creation step; it does not move the approval gate.

## What it provides

1. **One-line model.** Plans are written in the izzi repository and published
   to the portal with one approval-gated command
   (`scripts/publish-plan-proof.mjs`). The page itself never creates or
   submits anything.
2. **Three-step ladder.**
   - Scaffold: `make plan-vertical-scaffold NAME=<vertical>
     CONCEPT="one-line concept"` in izzi produces the starter
     `plan-draft-v1.md`.
   - Write to the stage: a draft needs only provenance and a bounded
     document; a vertical adds template, segments, estimates, pilot options,
     and gates; a formal plan adds orchestration (and a PDF variant needs a
     PASS special-topics check via `--checks`).
   - Publish from the situationshipin.space repo root with
     `--approve PROJECT-APPROVED`, then commit and push; GitHub Pages
     deploys and the plan appears newest-first on `plans.html`.
3. **Copyable command template** for each stage, with the `--dry-run` form
   first and the real command second.
4. **Stage table** showing what each of `draft`, `vertical`, and `formal`
   requires, so an author picks the right stage before writing.
5. **Fine print:** `PROJECT-APPROVED` is the explicit project-approval gate;
   plan documents are capped at 16 MiB; a `KEEP` on an earlier stage
   advances the plan, a `KEEP` on the formal plan unlocks the draft loop;
   review drafts stay browser-local; commit and push only after the script
   passes its own validator.

### Optional Phase B — client-side command builder

A small form (vertical slug, title, description, family, feedback round,
stage) that composes the exact `publish-plan-proof.mjs` invocation and a
"Copy command" button using `navigator.clipboard`. No uploads, no network
calls, no persisted form state. Rationale: removes artifact-id/argument
typos without weakening the static-site policy. Phase B can be approved
separately from Phase A.

## Implementation

- **`plans.html`:** insert one new
  `<section class="new-section" aria-labelledby="new-title">` between the
  Status summary and the Review section. Keep every existing required id and
  the `data-review-category="planning"` attribute in place.
- **`assets/css/review.css`:** reuse the existing `section-heading`,
  `selection-panel`, `button`, and `button-secondary` classes; add only a
  minimal `.new-section` / `.command-block` rule so the page keeps one
  visual system.
- **`assets/js/review.js`:** Phase A needs no JavaScript. Phase B adds a
  page-scoped builder block keyed to `data-review-category="planning"`,
  preserving the checker's existing string markers (`pageSize: 10`,
  `AESTHETIC_DECISIONS`, `source_image_sha256`, `style-processing-page-`,
  `Suggested Codex handoff`, `review_identifier`,
  `public_submission_acknowledged`).
- **Validator parity:** add a required-id-style assertion in
  `scripts/check-review-site.mjs` that `plans.html` contains `id="new-title"`
  so the section cannot silently regress.
- **Build receipt:** after the edits run
  `node scripts/update-build-manifest.mjs` then
  `node scripts/check-review-site.mjs`; the checker verifies the recorded
  code hashes against the working tree.

## Constraints the new copy must respect

From the current `check-review-site.mjs` planning contract:

- `plans.html` keeps these ids: `review-catalog`, `artifact-grid`,
  `artifact-template`, `filter-form`, `download-feedback`,
  `import-feedback`, `issue-dialog`, `reset-dialog`, `previous-page`,
  `next-page`, `page-status`, `results-title`, `results-description`.
- Category isolation: the page must not contain the exact strings
  `Style processing` or `Proofs for inspection`, so the new-section copy
  must avoid those phrases.
- No remote script or stylesheet; keep the `public GitHub issue` disclosure
  text; keep `data-review-category="planning"`.

## Acceptance

- The New section renders above Review on desktop and mobile with sensible
  heading order and ARIA.
- The command template matches the README invocation exactly, and the
  `--dry-run` step is shown before the approval-bearing command.
- The Phase B builder (if approved) produces the same arguments as the
  template, and copies without any network request.
- `check-review-site.mjs` passes after `update-build-manifest.mjs`, and the
  review/handoff behavior of the page is unchanged.

## Gates

- The edits are in the situationshipin.space repository, which is outside
  this session's writable roots; implementation requires the user's explicit
  authorization to edit that repository.
- Zero provider spend.
- Commit and push of the portal only on explicit user request.
