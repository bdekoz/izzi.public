## 3. Scope interpretation

**Tune** means adjust the nine landed families' defaults and parameter
interpolation against the reference geometry: sunburst ray spacing,
band-guilloche rail/centerline logic, fish-scale overlap seams, barleycorn
stagger, medallion frame proportions, vignette falloff, multicolor-line iris
ramps, flinque overlay transparency, and the accessibility profile density
budgets.

**Extend** means two bounded additions, in priority order:

- P4 — full JSON scene-authoring for the new composition geometries plus the
  scene schema contract.
- P5 — a latent-image microline band (direction-modulated lines), feasible
  with the existing stroke pipeline.

Lenticular/interlaced arrays stay deferred: they need print-resolution
strip rasterization, conflict with the "no testing / no image production"
constraint, and add no review value in a stroke-SVG pass.

## 4. How the sol-5.6 API round would run

Per the official OpenAI documentation (OpenAI Docs):

- Model: `gpt-5.6-sol` (the `gpt-5.6` alias routes here). Input modalities
  text + image, output text, 1,050,000 context window, 128,000 max output
  tokens, reasoning tokens supported.
  [Model page](https://developers.openai.com/api/docs/models/gpt-5.6-sol)
- Endpoint: Responses API (`/v1/responses`). Tools used: `apply_patch` for
  code edits and structured outputs for a per-package change manifest.
  `hosted_shell`, `code_interpreter`, and `image_generation` stay disabled —
  they are outside the code-changes-only, images-read-only scope.
- Reasoning: standard mode; `reasoning.effort` high for design turns (P1/P3/P5),
  medium for mechanical edits. Pro mode is not used.
- Conversation: multi-turn with `previous_response_id` so the source +
  reference prefix is prompt-cached; GPT-5.6 defaults reasoning context to
  `all_turns`.
- Deliverable per turn: a patch (or patches) plus a JSON change manifest
  (files touched, changed symbols, rationale). A human or Codex applies and
  compiles locally; sol-5.6 never tests.

## 6. Reference-image policy (no text, no numbers)

Each work package's prompt states the policy explicitly: the 18 photographs
are geometry references only. Sol-5.6 may use curves, band spacing, scale
texture, rosette structure, and vignette falloff; it must ignore and never
reproduce lettering, numerals, serials, or other typographic elements. This
is a prompt-enforced scope rule; no image preprocessing is required beyond
the resize below, and no image output is produced.

## 7. Compression / packaging recommendation

The billed unit is tokens, not bytes, so byte compression does not reduce
cost. The two real optimizations are resizing the references and keeping
the prompt prefix stable for caching.

**Sources — no compression, plain text.**

- The three headers are 224 KB and the four examples 79 KB (303 KB total).
  Send them as one text bundle with `// ==== FILE: <path> ====` separators,
  full fidelity, nothing stripped.
- A zip/tar adds a decode step, hides structure, and saves nothing on the
  token meter. Not recommended.

**References — resize, then base64 (or file search).**

- Full resolution bills at the 32px-patch rule from the official
  images-and-vision guide: each 2252x4000 (or 4000x2252) image is
  `ceil(2252/32) x ceil(4000/32)` = 71 x 125 = 8,875 image tokens. The
  full set is 159,750 tokens (about $0.80 per read at the $5/MTok input
  rate).
- Resized to 1024 px on the short side: 32 x 57 = 1,824 tokens each,
  32,832 for the set (about $0.16 per read) and roughly 6 MB of JPEG at
  quality 82. This is the recommended default; the official guide likewise
  recommends resizing before sending.
- Full-resolution zoom is allowed only for up to 3 images per zoom turn and
  at most 6 zoom turns total.
- Transport: base64 data URLs for the resized set (18 small images, ~8 MB
  after +33% base64 overhead) is simplest; use the Files API with
  `file_search` if the same set must be referenced across many turns
  without re-uploading. Storage pricing was not established from the pages
  reviewed here, so base64 is the default.

## 8. Cost estimate against the $50 balance

1M tokens): input $5.00, cached input $0.50, cache writes $6.25, output
$30.00. Inputs over 272K tokens bill at 2x input and 1.5x output for the
whole request; Batch/Flex halve the standard rates; Fast mode doubles them.
Reasoning tokens are billed as output tokens.

## 9. Can this be done in Codex?

Yes — and it is the recommended executor for this repository, because the
restriction "code changes only, no testing" is the sol-5.6 constraint, not
a Codex constraint.

Per the official Codex CLI documentation, Codex inspects files, makes
edits, and runs the tools already installed on the machine against the
local repository, with sandbox and approval controls; `codex --image`
brings a design reference into the prompt.
[Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

Concretely, Codex in this session can:

- read the three headers and four examples directly from the checkout;
- read the 18 reference JPEGs locally (no upload, no image-token billing);
- apply the same P1-P6 changes, then compile and run the existing
  `guilloche-capability-review` / scene-json targets — testing that the
  sol-5.6 path is forbidden from doing;
- update `docs/generative_patterns/` and publish the v2 portal index with
  the established publish script.

Tradeoff table:

| Axis | sol-5.6 via API | Codex (this session) |
|---|---|---|
| Cost against the $50 key | ~$16-25 disciplined, ~$79 worst case | no draw on the key |
| Testing | forbidden by the brief | local compile + make targets |
| References | token-billed API reads | local file reads |
| Output control | patches + manifests only | direct edits + local verification |

Recommendation: implement in Codex at zero API spend. If the intent is
specifically to have a second, differently-trained model author the changes,
use a hybrid — sol-5.6 drafts per-package patches at the scenario-3 spend
bound, and Codex applies, compiles, and fixes integration drift locally.

## 11. Reply — can the API key be used with sol-5.6 in Codex?

Yes. Codex can run `gpt-5.6-sol` against the existing API key; the model,
reasoning effort, and provider are all client configuration per the official
OpenAI documentation.

Wiring (from the official Codex configuration and environment-variable
docs):

- Select the model with `model = "gpt-5.6-sol"` in `config.toml` or
  `codex --model gpt-5.6-sol`; the configuration examples show GPT-5.6-family
  model selection directly.
- Supply the key either by pointing the built-in `openai` provider at the API
  (`openai_base_url` plus `OPENAI_API_KEY`), or with a custom
  `model_providers.<id>` entry using
  `base_url = "https://api.openai.com/v1"` and `env_key = "OPENAI_API_KEY"`.
  Export `OPENAI_API_KEY` from the existing key file in the process
  environment; do not hardcode the key material in `config.toml`.
- If `gpt-5.6-sol` is not in the client's built-in model list, add it through
  `model_catalog_json` (a catalog of available models).
- `CODEX_API_KEY` is only for non-interactive `codex exec` runs; provider
  keys use `env_key` as above.

Two caveats that change the cost picture:

- With API-key auth, Codex requests bill to the key at the section 8 API
  rates, so this path **does draw the $50 balance**. The section 9 "no draw
  on the key" statement applies to normal ChatGPT/Codex plan authentication,
  not to API-key-backed runs.
- Key holders still need model access on the account. Confirm
  `gpt-5.6-sol` is available to the key (platform model availability or
  `GET /v1/models`) before committing spend.

Net effect: sol-5.6 inside Codex gets the local file editing, image reading,
and optional build tooling that the raw Responses API round lacks, while
billing the key at the same token rates. The brief's no-testing rule then
becomes a scope choice rather than a capability limit.
