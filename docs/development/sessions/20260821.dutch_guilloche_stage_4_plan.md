## 3. Scope interpretation

**Tune** means add one new, additive composition preset that matches the
reference motif rather than touching the nine accepted families: a
two-layer radiating burst whose layers are tuned independently (outer
brown, inner blue), parameterized for radius ratio, ray count, angular
span, phase, and per-layer stroke behavior. Existing composition defaults,
accepted plate filenames, and the P1-P5 series stay byte-stable.

**Extend** means three bounded additions, in order:

- E1 — `dutch_radiate_tuning` + `make_dutch_radiate(origin, radius, tuning)`
  in `src/izzi-svg-guilloche.h`, building on `composition_kind::sunburst`
  and the existing plate/layer machinery, plus authorized enum/schema
  evolution (a new `pattern_family` value and scene-JSON metadata);
- E2 — a new example `examples/guilloche-dutch-review.cc` that renders the
  3×5 review plate in §1.6, one grid SVG plus one per-cell SVG;
- E3 — docs/tests/wiring: `docs/generative_patterns/guilloche.md`,
  `CMakeLists.txt` target `izzi_guilloche_dutch_review`, `Makefile`
  `guilloche-dutch-review` / `guilloche-dutch-check`, and one deterministic
  baseline under `tests/baselines/`.

House rules carried forward: existing accepted plates stay stable; the new
pass is a separate example and a separate portal review family; it does not
edit `generation-guilloche-20260816-index` or the v2 family.

  immediately.
- Conversation: multi-turn with `previous_response_id` so the source prefix
  is prompt-cached; the reference image travels once in the prompt prefix.
- Deliverable per turn: patches plus a JSON change manifest (files touched,
  changed symbols, rationale). A human or Codex applies and compiles

## 7. Compression / packaging recommendation

The billed unit is tokens, not bytes, so byte compression does not reduce
cost. The real optimizations are resizing the reference and keeping the
prompt prefix stable for caching.

**Sources — no compression, plain text.**

- The three headers are 277 KB and the four examples 79 KB (356 KB total,
  ≈85-90K text tokens). Send them as one text bundle with
  `// ==== FILE: <path> ====` separators, full fidelity, nothing stripped.
- A zip/tar adds a decode step and saves nothing on the token meter.

**Reference — crop, resize, then base64.**

- Full resolution bills at the official 32px-patch rule:
  `ceil(2252/32) × ceil(4000/32)` = 71 × 125 = 8,875 image tokens for the
  single target (~$0.044 per read at the $5/MTok input rate).
- Crop the lighthouse/minaret apex to the radiating pattern and resize to
  1024 px on the short side: ~1,824 image tokens (about $0.009 per read) and
  roughly 0.3-0.5 MB of JPEG. This is the default; full-resolution zoom is
  capped at 3 zoom turns.
- The other 17 photographs are not needed this round and are not uploaded.
- Transport: base64 data URL in the prompt prefix; the Files API with
  `file_search` only if the same crop must persist across many turns.

## 8. Cost estimate against the $50 balance

Official rates for `gpt-5.6-sol` (standard processing, per 1M tokens):
input $5.00, cached input $0.50, cache writes $6.25, output $30.00. Inputs
over 272K tokens bill the full request at 2× input and 1.5× output;
Batch/Flex halve the standard rates. Reasoning tokens bill as output.
[Pricing](https://developers.openai.com/api/docs/pricing) ·
[Reasoning](https://developers.openai.com/api/docs/guides/reasoning)

Planning token figures:

| Input | Estimate |
|---|---|
| Three headers + four examples (356 KB) | ~85-90K text tokens |
| One reference crop, 1024 px short side | ~1.8K image tokens |
| Task brief + manifests per turn | ~2-5K tokens |
| Reasoning + visible output per design turn | ~15-25K tokens |

Scenarios (standard processing unless noted):

| Scenario | Math | Total |
|---|---|---|
| 1. Image read only (D1) | input ~5K ($0.03) + output ~2K ($0.06) | ~$0.10 |
| 2. One-shot survey (D1+D2) | input ~95K ($0.48) + output ~25K ($0.75) | ~$1.25 |
| 3. Full round D1-D4, ~15 turns, cached | turn 1 cache write ~95K ($0.59) + output ($0.60) ≈ $1.20; turns 2-15: cached read ($0.05) + new input ~4K ($0.02) + output ~12K ($0.36) ≈ $0.43 each = $6.0; ≤3 zoom turns ≈ $0.5 | ~$7-8 |
| 4. Full round with Batch/Flex for mechanical bulk | about half the per-turn model fees | ~$4-5 |
| 5. Worst case: uncached every turn, full-res reference | 15 × (input ~$0.50 + output ~$0.75) | ~$19 — still inside $50 |

Verdict: the recommended path (scenario 3, or 4 if latency allows) fits
inside $50 with roughly $42 headroom. The single-image scope makes the
worst case benign; the only real risk is uncapped reasoning output.

## 9. Can this be done in Codex?

Yes — and it is the recommended executor for the code side, because "code
changes only, no testing" is the sol-5.6 constraint, not a Codex constraint.
Codex in this session can read the headers and examples directly from the
checkout, apply D2-D4, then compile, run the example, render the SVGs, and
verify the deterministic baseline locally at zero draw on the key.

One caveat for this specific round: the reference read cannot be done
visually by the local agent in this session (no image-input support), and
local numeric image analysis was explicitly rejected by the human. So the
image read (D1) goes through sol-5.6 vision at the scenario-1 cost, and the
code work is Codex-local or a sol-5.6 hybrid:

| Axis | sol-5.6 via API | Codex (this session) |
|---|---|---|
| Reference image read | sol-5.6 vision, ~$0.10 | not available locally |
| Code changes | patches + manifests, ~$7-8 round | direct edits, zero key draw |
| Testing / image production | forbidden by the brief | local compile + render + baseline |
| Output control | bounded by caps/guardrails | direct local verification |

Recommendation: hybrid — sol-5.6 performs D1 (and, if directed, drafts
D2-D4 patches), and Codex applies, compiles, renders, and verifies locally.
