Two existing defects are in scope because they interact with this work:

- **Off-screen routes.** The fixed `setView` centers on Frogtown
  (34.107, -118.248). Hammer Museum's route (≈34.0579–34.0620,
  -118.4429–-118.4532) is centered roughly 0.2° of longitude west, several
  frame-widths off-screen at zoom 15 — hence "doesn't show the route at
  all".
- **Clear saved path corrupts the catalog in memory.** The reset handler
  runs `current.route.points = null` and hardcodes
  `locationSelect.value = "frogtown"`. The first line permanently breaks
  the previously selected location for the rest of the session
  (`current.route.points.map(...)` throws on re-selection); the second
  breaks as soon as the catalog no longer has a `frogtown` entry. Clearing
  a saved path should never mutate the loaded catalog.

## 3. Design decisions

The site is static and browser drafts are explicitly local ("Drafts stay in
this browser"). The browser therefore cannot write `data/locations.json`;
new paths have to follow the same handoff already used for reviews:
author locally, then export as review JSON or a GitHub issue draft, and a
human folds the accepted path into `data/locations.json` repo-side.

Decisions:

1. **New paths are named, browser-local drafts.** A new path gets a
   user-entered name (slugified to a `location_id`), an ordered set of
   map-clicked waypoints, and persists in `localStorage` until cleared.
2. **Drafts are selectable like catalog locations.** They appear in the
   Location dropdown under a `Local drafts` optgroup so they survive
   reloads and can be re-edited. Catalog entries remain the source of
   truth; drafts are additive and never replace catalog data in memory.
3. **Existing export buttons carry the draft.** Download and GitHub-issue
   buttons already serialize the active record, so a new-path record just
   needs additive draft metadata (`origin: "new-draft"`, `display_name`,
   `slug`) and the issue-draft builder emits a "New location proposal"
   title/body instead of a review title.
4. **Fit on selection, not on drag.** The map fits the route bounds once
   when a location or draft is opened; dragging a marker does not refit
   (that would fight the user's zoom/pan).
5. **No new network calls, no new remote scripts.** Leaflet and OSM tiles
   are unchanged; everything else stays inline and localStorage-backed.

## 4. Feature design — New path

### 4.1 Control

Add `<button type="button" id="new-path-button" class="button
button-secondary">New path</button>` immediately before the existing reset
button in `#location-form`. `type="button"` matters: a default submit
button would reload the page. The `.filter-grid` CSS already positions the
two buttons side by side on desktop and stacks them on mobile.

### 4.2 Authoring flow

Clicking **New path** switches the page into authoring mode:

1. The selection panel reveals a name field
   (`<input id="new-path-name" placeholder="e.g. Sunset pass">`) and a
   **Save path** button, and shows helper copy: "Name the path, then click
   the map to add waypoints; drag markers to adjust."
2. The Location dropdown selects a synthetic draft entry (shown under
   `Local drafts`), and the map opens on a default Los Angeles view.
3. Clicking the map adds a draggable marker, labeled `point-0`, `point-1`,
   … in click order (consistent with the labels already used in
   `locations.json`). Each new point rebuilds the polyline and the point
   list through the existing `updateRoute()`.
4. **Save path** validates that a name is present and at least two points
   exist, slugifies the name (`Sunset pass` → `sunset-pass`; lowercase,
   spaces to hyphens, drop other non-`[a-z0-9-]` characters, append `-2`,
   `-3`, … on collision with an existing draft), and writes the record.
5. Selecting a catalog location, the project dropdown, or **Cancel** exits
   authoring mode without discarding saved drafts.

### 4.3 Storage model

One localStorage key per draft, kept read-compatible with the existing
schema (additive fields only):

```json
{
  "schema_version": "izzi-web-location-review-1",
  "review_id": "review:location-scouting:new-draft:sunset-pass",
  "project_id": "here-lies-trouble",
  "location_id": "sunset-pass",
  "origin": "new-draft",
  "display_name": "Sunset pass",
  "decision": "UNREVIEWED",
  "note": "",
  "points": [
    { "label": "point-0", "lat": 34.099, "lng": -118.296 }
  ],
  "at": "2026-08-17T12:00:00.000Z"
}
```

Key space: `review:location-scouting:new-draft:<slug>`, so drafts can never
collide with catalog keys (`review:location-scouting:<location_id>`).
Existing `savedReview()` readers ignore the extra `origin` /
`display_name` fields.

### 4.4 Handoff to the repo

- **Download review JSON** keeps working as-is; the filename becomes
  `<project_id>-new-<slug>.review.json` for drafts.
- **Open GitHub issue draft** switches to title
  `New location proposal: <display_name>` with a body noting the path is a
  local draft and listing waypoints the same way reviews do. The repo-side
  step — add the accepted route to `data/locations.json` and commit — stays
  human and approval-gated, matching the existing issue flow.
- Optionally render a copyable JSON fragment shaped like a
  `locations.json` entry to speed the repo-side merge; recommend as a
  follow-on, not part of the first cut.

## 5. Feature design — route fit-bounds

Replace the hardcoded `setView([34.107, -118.248], 15)` in `renderMap()`
with a fit step that runs after the markers and polyline exist:

```js
function fitRoute() {
  if (!markers.length) return;
  if (markers.length === 1) {
    map.setView(markers[0].marker.getLatLng(), 17);
    return;
  }
  const bounds = L.latLngBounds(markers.map(function (entry) {
    return entry.marker.getLatLng();
  }));
  map.fitBounds(bounds.pad(0.25), { maxZoom: 17 });
}
```

Rules:

- Call `fitRoute()` only from `selectLocation()` / draft-open paths, never
  from the marker `dragend` handler, so adjusting points does not yank the
  viewport.
- `pad(0.25)` guarantees margin around the outermost markers (Hammer's
  three points span ~450 m north-south and ~900 m east-west, so it needs
  roughly zoom 16–17 to fill the frame).
- `maxZoom: 17` prevents over-zooming tiny routes; a one-point route uses
  `setView` at zoom 17 instead.
- If `map.fitBounds` is called before the frame has its final size, call
  `map.invalidateSize()` once after mount as a guard.

Acceptance: Frogtown still opens legibly; Hammer Museum, MOCA Geffen,
Hauser & Wirth, and Runyon show their complete paths immediately after
selection.

## 6. Related fixes bundled with this change

Because the reset handler is the immediate neighbor of the new button and
currently corrupts the catalog, fix it in the same pass:

1. Never null `current.route.points`. Clearing should remove only the
   localStorage record(s) for the active location/draft.
2. Replace the hardcoded `"frogtown"` with the project's first catalog
   location (or the currently selected entry) and re-render cleanly.
3. Decide the label/behavior ambiguity: one localStorage record currently
   holds both the adjusted points and the human review, so **Clear saved
   path** also clears decision/note. Keep that behavior but document it in
   the helper text, or split points and review into separate keys. The
   recommended first cut is to document it; key-splitting is a separate,
   optional change.

The pending-coordinates branch ("Coordinates pending — add them here when
scouted") is a natural second consumer of click-to-add mode. Out of scope
here, but the authoring-mode code should be written so a pending location
can later open in the same mode.

## 8. Constraints to respect

- Static site: no server writes; new paths live in `localStorage` and reach
  `locations.json` only through the human issue/commit flow.
- No remote scripts or stylesheets beyond the existing Leaflet CDN, and no
  account token, analytics, autoplay, or source media.
- Keep existing ids (`route-map`, `point-list`, `route-note`,
  `location-form`, `review-form`) and `data-review-category="location-scouting"`.
- Keep schema `izzi-web-location-review-1` readable by the existing
  `savedReview()` / `restoreDraft()` code; draft fields are additive.
- Draft slugs must be sanitized before becoming keys or filenames.
