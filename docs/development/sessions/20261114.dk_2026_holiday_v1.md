# De Kosnik holiday 2026: whole-photograph DLH studies

## Decisions

The user requested a new `dk-2026-holiday-v1` series using the five photographs
in `resources.rizal/de-kosnik-2026`. The final corrections specify **four
variations per photograph**, the native portrait API applied to **the entire
photograph**, **different mixed DLH allocations**, **strong contrast**, and
**varying flow**. DLH means dot / line / cross-hatch. The initial three-version
idea and the subsequently suggested equal-plus-three-pure set were superseded.

Guilloche colors come from each photograph. Ornament should develop from
what is happening in that picture, carrying forward the complexity of stage 3
without reusing its unrelated palettes or isolated-face compositions. This
series is twenty individual designs, not anniversary front/back pairs.

The source and recipe record
contains the exact four mixtures and physical controls. Contrast is 1.65 in
all cases. The straight equal-DLH version retains independently curved source
contours and decorative geometry; zero turn applies to the photo cut flow.

EXIF orientation is respected. Full-image support is one everywhere, and
feature protection is zero everywhere. Original files are never modified.
The five palette roles each record an actual source pixel, its RGB value,
authored sample rectangle and selection rule. Derived paper and dark-border
tints are explicit mixtures, not additional stock palettes.

The composition field combines unequal pitches, authored normalized scene
landmarks and a blurred 128 x 128 full-photo luminance-gradient field with
bilinear sampling. Scene ornament runs across the photographic background
and surrounding sheet. A chain of vector clips reduces overlay detail over
people and key gestures; it never removes native photographic marks.

## Implementation

`scripts/dk2026_holiday.py` prepares oriented full-image luminance planes and
palette receipts, builds the existing C++ driver, and caches native renders
by complete input and executable signature. `render-dk-2026-holiday-v1.py`
composes the field and photographic geometry, outlines real-font lettering,
and exports the gallery, PNGs and vector PDFs. The validator checks original
hashes, source pixels, support planes, all embedded native marks, physical
sizes, intended recipes, vector purity, page counts and independent replay.

The native driver gained two explicit banknote overrides: `analysis_long_edge`
and `coverage_sample_mm`. Existing defaults remain unchanged. Their receipt
values are covered by the driver regression. No change to the core portrait
API or banknote engine was required.

Whole photographs use a 1200-pixel input, 800-pixel tensor analysis and 0.05 mm
coverage sampling. Geometry is generated at 130 mm width for landscape
photographs and 98 mm for the portrait photograph, then translated into place
without scaling. The final cards are 7 x 5 inches and 5 x 7 inches respectively.

## Delivery and validation

All twenty designs, SVGs, 600 dpi PNGs, gallery and both PDFs are generated.
The validator passes **686 checks and twenty independent native replays**.
All twenty print pages agree with their SVG raster exports at 600 dpi; the
maximum normalized RGB mean absolute error is **0.001405**. The native driver
regression and strict C++20 compilation pass.

Representative compositions from all five photographs and the H01 comparison
page were visually inspected. The comparison PDF contains some Cairo 300 dpi
raster fallbacks; the individual SVGs and twenty-page print PDF retain vector
artwork. An initial comparison using Poppler's Splash rasterizer overestimated
thin-line differences; matching Cairo scan conversion reduced the maximum
error to the value above. The original measurements remain in the output
validation folder.

The gallery,
comparison PDF
and print PDF
are preserved. Durable validation
and review receipts
record the checks and artifact hashes. A physical printer proof has not been
performed.

The user subsequently requested a smaller photographic area, blended edges,
colored engraving and ten palette variations per photograph. That revised
composition is recorded in the separate [v2 plan](20261114.dk_2026_holiday_v2.md).

## Reproduction

```sh
python3 scripts/render-dk-2026-holiday-v1.py --deliver
python3 scripts/check-dk-2026-holiday-v1.py --replay
python3 tests/portrait-driver.py build/dk-2026-holiday-v1/portrait-engraving
```

Generated media remain under the ignored `outputs/dk-2026-holiday-v1/`
directory; source recipes, generators, documentation and durable validation
receipts are repository material. This series is included in the subsequent
commit/push request recorded in `20261114.dk_2026_holiday_v4.md`.
