## 1. Directive, normalized

Create two single-channel, 1080×1920 portrait shorts under the project title
`danmaku wind`:

1. `danmaku wind anthropocene` (`DMX1`), using every dyad in the
   Anthropocene codex's chronological section, PDF pages 16–39.
2. `danmaku wind art` (`DMX2`), using every dyad in the art codex's
   chronological section, PDF pages 17–28.

For both shorts:

- USER text is `mode:reverse` and uses the Wind font.
- ASSISTANT text is `mode:scroll` and uses Atkinson Hyperlegible Next.
- The semantic text from each day page is a fixed `mode:top` run.
- Each dyad's complete five-part identity block is a fixed `mode:bottom`
  run.
- Dyads remain in source chronology. Text is reflowed only to make display
  chunks; it is not summarized, shortened, corrected, or rewritten.
- The product is exactly one video file per short, two video files total.

The user approved this plan and authorized unattended local implementation.
The implementation renders both shorts without modifying the danmaku core,
downloading a font, publishing, committing, or pushing.

## 3. Normalized conversation contract

The parser produces one deterministic JSON document per short. Every record
retains the source PDF hash, physical page number, printed date/page index,
dyad ID, time, group, short hash, role, normalized display text, and a hash
of that text.

### 3.1 Extraction

1. Invoke `pdftotext -raw` one physical page at a time within the exact
   requested range; page boundaries are never inferred from the flattened
   whole document.
2. Classify each page as section opener, day page, dyad page, or continuation
   dyad page.
3. Remove only exact codex furniture: repeating `BOUNDARY OBJECTS CODEX`
   headers, printed `PAGE n`, and isolated footer folios.
4. Parse day pages into the source date, `OBSERVED SOURCE DATE /
   AMERICA/LOS_ANGELES`, and entry-count sentence.
5. Parse each dyad header with strict patterns for `BOC-DYAD-nnnn`, time,
   `BOC-GROUP-nn`, and the 12-character hash. Read the page heading for
   `YYYY-MM-DD / n`.
6. Split content only at the literal `USER` and `ASSISTANT` role markers.
   Visual line wraps are joined with spaces; paragraph/code boundaries and
   Unicode punctuation remain represented. `UNAVAILABLE — no assistant
   response in the bounded source.` remains literal assistant content.
7. Join entries spanning two physical dyad pages before display chunking.

Hard parser assertions:

- DMX1 has 11 day records and exactly the 33 verified dyad IDs in source
  order.
- DMX2 has 6 day records and exactly the 12 verified dyad IDs in source
  order.
- Every dyad has one USER field. ASSISTANT fields are retained exactly when
  present, including the explicit source `UNAVAILABLE` value. Six
  Anthropocene dyads have no ASSISTANT field in the PDF and are recorded as
  `missing_from_pdf`; implementation does not invent their responses.
- Each date's parsed dyad count equals its day-page count.
- No requested page is unclassified and no text remains unaccounted for
  except allowlisted page furniture.

### 3.2 Fixed top and bottom runs

The active day record stays visible in the top band for all dyads belonging
to that day. Its semantic text is rendered as `mode:top`, for example:

```text
2026-08-06
OBSERVED SOURCE DATE / AMERICA/LOS_ANGELES
3 codex entries in this day.
```

The active dyad identity stays visible in the bottom band for that dyad's
entire scene. It is rendered as a logical `mode:bottom` block in this exact
field order:

```text
BOC-DYAD-0231
01:50:15
2026-08-06 / 1
BOC-GROUP-04
b4909414cdfb
```

The current izzi run type is single-line. The compositor will therefore
represent each logical fixed block as linked top/bottom line runs sharing a
`logical_run_id`, source span, start, and duration. All constituent lines
retain the required mode; no new multiline core type is needed.

### 3.3 USER and ASSISTANT chunks

Long role messages are split on paragraph, sentence, clause, and finally
word boundaries until each outline-measured line fits its maximum display
width. Chunk reassembly, after removing only introduced display separators,
must equal the normalized role text exactly.

- USER chunks: `mode:reverse`, Wind VF with a complete animated
  `WIND` 0°→360° cycle, right-to-left.
- ASSISTANT chunks: `mode:scroll`, Atkinson Hyperlegible Next Regular,
  left-to-right.
- USER chunk start times precede ASSISTANT chunk start times within a dyad.
  The assistant phase begins when the final USER chunk has entered its lane;
  the phases may overlap in flight but cannot reverse source order.
- No summary, ellipsis, line cap, or `max-runs` truncation is permitted.

## 4. Visual and timing proposal

### 4.1 Frame and hierarchy

- Canvas: 1080×1920, square pixels, 30 fps.
- Background: print-style 10% gray (`#E6E6E6`, 10% black / 90% white); no
  source imagery and no generated/provider imagery.
- Safe area: 64 px horizontal, 96 px vertical.
- Top day band: approximately y=96–280.
- Conversation field: approximately y=310–1580.
- Bottom dyad band: approximately y=1610–1824.
- USER: black `#000000`, Wind, approximately 50 px.
- ASSISTANT: white `#FFFFFF`, Atkinson Next Regular, approximately
  44 px.
- Day top: black `#000000`, Atkinson Next SemiBold, approximately 40 px.
- Dyad bottom: charcoal `#303030`, Atkinson Next SemiBold, approximately
  32 px.
- Text is fill-only with no stroke. The user-approved white ASSISTANT fill on
  10% gray is an intentional art-direction exception to the earlier 4.5:1
  contrast target; verification records the measured fill contrast and
  inspects the requested composite rather than silently changing either
  color or adding an outline.

The type sizes are starting values, not an excuse to clip. A preflight
measures actual Wind and Atkinson outlines and may reduce a role by at most
10% to satisfy the safe-area contract; a larger reduction stops for review.

### 4.2 Title and ending

Each short opens with a 2.0-second title card:

```text
danmaku wind
danmaku wind anthropocene|art
chronological codex
```

`chronological codex` is source text for DMX1 and a shared project label for
DMX2. The final dyad completes normally, followed by a 1.0-second hold on the
project title. There is no credit roll or extra video.

### 4.3 Content-derived duration

The complete source is more important than forcing an arbitrary runtime.
Moving chunks use a 4.8-second traversal with deterministic,
collision-aware lane scheduling. A chunk enters at the earliest time that
does not collide with another run in its direction/lane. Each dyad scene ends
0.5 seconds after its final moving chunk exits; fixed top/bottom runs span the
whole scene.

Exact durations are computed only after font-aware chunking and recorded in
the timeline manifest. Based on the verified source size, the expected order
of magnitude is 5–9 minutes for DMX1 and 2–4 minutes for DMX2. If either
computed duration falls outside those ranges, implementation stops and
reports the chunk/lane calculation instead of hiding content or changing
speed silently.

### 4.4 Audio

No audio source or sound direction is supplied. Both canonical MP4s are
video-only, with no silent placeholder audio stream. Audio can be proposed as
a later revision without changing the source/timeline contract.

## 5. Technical design

### 5.1 New renderer

Add `scripts/render-danmaku-wind.py` with three explicit operations:

```text
extract   PDF -> normalized conversation JSON
plan      conversation JSON + fonts -> resolved timeline/overlay manifests
render    resolved timeline -> canonical MP4 + non-video audit artifacts
```

The script reuses font loading, outline extraction, hashing, and verification
helpers from `scripts/compose-vector-overlay.py`, and invokes the existing
`examples/text-overlay.exe` emitter. Shared helpers may be moved into a small
importable module only if that can be done without changing the existing
compositor's behavior.

### 5.2 Cached vector-run atlas

The time-to-die proof regenerates and rasterizes a full SVG for every frame;
that is unsuitable for these much longer, text-heavy shorts. The new renderer
will instead:

1. Resolve every logical run to izzi glyph paths once.
2. Emit and hash the canonical overlay/timing manifest once.
3. Rasterize each unique run into a tight transparent RGBA sprite once,
   caching by font hash, axis coordinates, text hash, size, stroke, and fill.
4. Position cached sprites per frame from the manifest's mode/start/duration
   math and alpha-composite them over the deterministic background.
5. Stream raw RGB frames directly to one ffmpeg encoder process; do not
   retain one PNG per frame.

The atlas is a rasterization optimization only. Source text, glyph outlines,
mode, lane, start, duration, font hash, axis instance, and fallback-glyph
provenance remain in the izzi manifest.

### 5.3 Encoding

Each output uses H.264 High Profile, 1080×1920, 30 fps, yuv420p, CRF 18,
`+faststart`, fixed color metadata, and no audio stream. Creation-time and
other volatile metadata are stripped. The renderer produces exactly these
video files:

```text
outputs/ad-hoc/danmaku-wind/danmaku-wind-anthropocene.1080p.mp4
outputs/ad-hoc/danmaku-wind/danmaku-wind-art.1080p.mp4
```

No review-proxy video is produced. Contact sheets and decoded still frames
are allowed because the one-video-per-short constraint concerns video
outputs, not audit sidecars.
